# Architecture and implementation plan

Milestone 1: one non-root Axum process serves a React application and a same-origin JSON API. OpenLDAP owns users, POSIX groups, salted passwords and account state. SQLite owns setup state, expiring sessions, monotonic Unix ID allocation, login throttling and administrative audit records. All administrative requests recheck LDAP administrator-group membership. Mutations require an exact configured Origin and a per-session CSRF token.

A separate, unexposed one-shot provisioning HTTP helper in the directory container creates a constrained slapd configuration and initial directory. It runs as the directory OS user, cannot accept commands or arbitrary LDIF, and refuses reinitialization. The manager never receives cn=config or root LDAP credentials. TLS uses an installation-local CA; the manager verifies its directory certificate. Installation secrets are files with restricted permissions outside Git. LDAP and management have independent lifetimes after provisioning.

Implementation sequence: provision TLS and deployment files; implement setup and LDAP authentication; implement user/group API and persistent metadata; implement responsive setup/login/dashboard and CRUD; run formatting, builds and integration tests against the real Compose stack; document recovery limits. Commit each working stage.

Milestone 2 adds host/SSSD/Ansible workflows as described below. Milestone 3 adds primary/replica replication and enrollment below. Milestone 4 adds: supported backup/restore, credential/certificate lifecycle and production hardening. No synthetic host or replication data will be presented as working features. Milestone 1 is a development release until security and failure checks pass. Setup uses a single instance; active/active managers are unsupported.

## Milestone 2 implementation plan

Add version-2 metadata for registered hosts, permitted LDAP group names, ordered LDAPS endpoints and configuration/export revisions. Host state describes configuration generation only; there is no resident agent or invented reachability data. Each export creates/rotates a dedicated read-only LDAP bind identity. Reusable host credentials are returned only in a protected archive, never persisted in SQLite. Existing installation ACLs already permit authenticated reads and forbid password reads and non-manager writes, so no privileged directory migration is needed.

Generate RFC2307 SSSD identity/password configuration with certificate verification and shadow account-expiry checks. PAM enforces allowed POSIX groups for SSH, preserving local recovery accounts; SSH access never grants sudo. Provide an Ubuntu Ansible role and equivalent manual instructions. Export revisions and group references prevent stale or silently broken policies. Deployable LDAPS endpoints need real DNS certificate SANs and explicit private-interface publication, independently of NPM.

Verify API authorization/CSRF, group dependencies, credential isolation/revocation, upgrades and persistence. Add an Ubuntu 24.04 client running actual SSSD, PAM and OpenSSH; test permitted/denied users, LDAP group updates, disabled accounts, passwords, TLS, endpoint fallback and Ansible idempotence. Multi-server replication remains Milestone 3.

## Milestone 3 implementation plan

Upgrade the primary's generated slapd configuration offline on container startup: enable syncprov, index entryUUID/entryCSN and grant narrowly named replication identities read access to password hashes. Preserve the MDB volume and refuse unrecognized configurations. Replicas use their own volumes, refreshAndPersist Syncrepl, verified provider TLS and readonly databases; no promotion or multi-provider writes.

A protected deployment archive contains a short-lived, one-use enrollment token (only its digest is stored in metadata), the provider CA and a replica Compose stack. The replica generates its private key locally and enrolls over verified manager HTTPS. The manager validates and pins a self-signed, non-CA server certificate scoped to the registered DNS hostname, creates an independent replication read identity and returns its credential once. No CA signing key enters the manager or a directory container. Host SSSD bundles include pinned replica leaf certificates for their configured endpoints. Expired/consumed tokens fail closed; failed enrollment requires an explicit new token.

Version-3 metadata records registered server endpoints, enrollment state, certificates and last actual checks/synchronization evidence. Monitoring binds over verified LDAPS and compares nonempty contextCSN sets; unavailable providers never imply confirmed synchronization. Existing authenticated administrators can read through enrolled replicas during a primary outage, with explicit read-only state. Mutations always require the primary. Test token expiry/replay, independent volumes, password/group/deletion replication, interruption/recovery, read-only enforcement, wrong certificates and real Ubuntu SSH failover with the primary stopped.

## Milestone 4 implementation plan

Deliver operator-run, age-encrypted consistent offline snapshots and fresh-target restoration. Verify authenticated decryption, a trusted externally recorded ciphertext checksum, strict archive paths/file hashes, SQLite integrity and native LDAP readability before publishing restored state. Restore clears sessions/pending enrollments, quarantines replica metadata, requires an explicit future Unix-ID floor, and leaves services stopped for network/fencing review. Failed restoration remains marked incomplete and cannot silently start. The WebUI receives maintenance/audit summaries, never Docker or CA signing authority.

Add a narrow local maintenance image/CLI for service-secret rotation with a durable recovery journal and native offline LDAP tools; keep reusable credentials out of logs/arguments. Extend replicas with staged local certificate generation/activation and controlled credential updates. The API supports dual certificate pins, verifies the actually presented new certificate before retiring the old manager pin, and marks affected host configurations for redeployment. Preserve primary CA trust when renewing its leaf. Record real maintenance events and certificate expiry, expose paginated audit history/export and session revocation, bound logs and improve failure/input handling.

Exercise encrypted backup/restore drills (including wrong key, corruption, unsafe archives, nonempty targets, session invalidation and ID allocation), failed-maintenance recovery, real secret/certificate rotation with Syncrepl/Ubuntu authentication, schema upgrades, and existing end-to-end suites. Document unverified platforms and security-review limits; production hardening does not imply an external security audit or automatic safe primary promotion.

## Guided replica setup

Server enrollment starts with a plain-language wizard explaining that the existing Forklift stack already owns the primary directory and the new machine only needs Docker. An operator-run preparation command renews the primary leaf with its LAN DNS name and persists private port publication; the manager has no Docker or CA access. The wizard verifies the exact primary leaf over a credential-free TLS connection before saving its reusable network address. A new replica bundle includes its private bind address, port and a single start script. A scoped, network-isolated one-shot helper copies enrollment material into a private volume without changing ownership of the operator's downloaded files. The runtime checks primary TLS reachability before redeeming its one-use enrollment token. Existing configured replicas still restart without contacting the primary or manager.
