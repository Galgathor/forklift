# DNS secondary servers

Forklift manages one writable PowerDNS primary and up to eight independent secondaries. Each secondary has its own SQLite database and serves previously transferred zones without Forklift or LDAP. There is no shared database, second management WebUI or automatic primary promotion. LDAP replicas and DNS secondaries are separate deployments and can run on the same second Docker host.

## Prepare the primary

The existing PowerDNS container in the primary stack is the DNS primary; do not create another server for it. In your Docker hosting tool, set `FORKLIFT_DNS_BIND` to that host's private interface and `FORKLIFT_DNS_PORT` to an available DNS port, then recreate the DNS container while retaining its volumes. The default `127.0.0.1` binding cannot accept transfers from another machine.

For example, publish `192.168.1.2:53` over **both UDP and TCP**. If another resolver owns that port, choose a separate private IP/host or a nonstandard port such as `1053`. Host-wide wildcard listeners can conflict with specific-address listeners. Do not replace your existing resolver or change host DNS settings. DNS cannot pass through an HTTP reverse proxy.

Open **DNS → DNS servers → Primary DNS endpoint**. Enter the same private address and published port and confirm they are reachable from the secondary. This endpoint is DNS traffic, not the LDAP, WebUI or native PowerDNS API port. Changing it saves new desired configuration; reconcile enrolled nodes afterward.

## Add a secondary

1. Create the forward/reverse zones you want to replicate in DNS.
2. Choose **Add DNS secondary**. Supply a friendly name, the second machine's private IPv4 interface, its DNS port (normally `53`) and a distinct private management port (normally `9544`). Select up to 32 zones. Forklift prepares the keys and native configuration; no existing DNS endpoint or manually configured certificate is needed.
3. Generate the DNS join configuration. Forklift's configured public URL must use HTTPS and be reachable from the new machine. If it uses private HTTPS PKI, paste its public CA certificate in the optional field. Never paste a private key. Publicly trusted HTTPS certificates need no additional CA.
4. On the second machine, open a checkout of this repository in your Docker Compose hosting tool and deploy `deploy/dns-secondary/compose.yaml`. It builds the pinned PowerDNS image from the repository. Paste the generated `FORKLIFT_DNS_JOIN=…` environment setting into that stack's deployment settings and start it within 15 minutes. No archive transfer is required.
5. Keep the `dns_secondary` volume. The container generates its own HTTPS private key, validates Forklift HTTPS, redeems its one-use token, creates a local SQLite database and provisions native Secondary zones. Once configured, restarts use persistent credentials even with an empty/expired join setting or an offline manager.
6. Return to Forklift and choose **Check synchronization**. Verify every assigned zone has matching primary/secondary authoritative SOA serials over UDP/TCP before directing client queries there.

The secondary uses Linux host networking so the selected interface must actually belong to that Docker host. Its DNS and HTTPS ports must be free before enrollment. It does not bind a wildcard LAN management listener. Restrict its private HTTPS management port to the Forklift host using host/network firewall rules; restrict DNS access to intended clients and peer servers. Allow TCP/UDP queries and signed transfers from secondary to primary, and UDP NOTIFY from primary to secondary. The primary source address seen by the secondary must match its registered primary; account for routing/NAT when placing peers on different networks. Blocked notifications delay updates until the next SOA refresh; reconciliation requests an immediate transfer. Publish only Forklift's WebUI through your HTTP reverse proxy. The native PowerDNS API stays on authenticated host loopback and is never forwarded through the secondary's HTTPS service.

The join setting contains a short-lived secret. Protect it in the Docker hosting interface and clear it after enrollment if desired. Generating a replacement invalidates a previous unused token. Expired, superseded or consumed tokens are rejected. If enrollment was consumed but its response was lost before the secondary saved configuration, remove the failed node in Forklift, preserve/retire that unconfigured stack, and deploy a new enrollment with fresh secondary storage. The WebUI never receives native API or TSIG credentials.

## Assignments, updates and diagnostics

**Assign zones** saves the desired selection; **Reconcile DNS server** applies it and requests a native refresh. Existing zone transfers then continue through native NOTIFY/SOA refresh without Forklift. New zones require an explicit assignment. Removing an assignment deletes only that enrollment's secondary copy. Confirmed primary zone deletion also removes its assignments; unavailable secondaries retain a visible retry error until reconciliation. Primary zone data is never deleted by deassigning a secondary.

Assigned Forklift-owned zones become native Primary zones; unassigned zones remain Native. Both stay editable in Forklift, including host-owned forward/PTR registration. Existing serial-increase policy is retained. Native transfers carry ordinary DNS zone data; PowerDNS comments and Forklift ownership metadata stay in the primary management installation.

The manager sets native transfer keys and zone metadata through the documented [PowerDNS API](https://doc.powerdns.com/authoritative/http-api/zone.html). Each secondary gets a separate HMAC-SHA256 TSIG key and only assigned zones authorize it. IP-only transfer exceptions, secondary retransfers and unauthenticated DNS UPDATE are disabled. Notifications are restricted to the registered primary IP and are unsigned: [PowerDNS signs each zone’s NOTIFY with only its first key](https://doc.powerdns.com/authoritative/settings.html#send-signed-notify), which conflicts with independent per-node transfer keys. A notification only prompts a refresh from the already-configured primary; the actual transfer still requires that secondary’s TSIG key. Native [AXFR transfers](https://doc.powerdns.com/authoritative/modes-of-operation.html) are used; the secondary may request IXFR, but PowerDNS Authoritative 5.1 serves a complete AXFR fallback rather than incremental IXFR data. There is no custom replication of SQLite files.

**Check synchronization** obtains fresh pinned-HTTPS diagnostics and actual authoritative SOA responses. A connected API, healthy container or responding server does not by itself mean synchronization succeeded. The dashboard shows per-zone expected and observed serials, primary reachability from the secondary, last check and last confirmed synchronization. These timestamps are observations, not continuous monitoring. If the primary is unavailable, current synchronization cannot be confirmed; the last confirmed time is retained. An unreachable management port reports management availability as unknown without claiming that DNS stopped.

Publish appropriate secondary NS/glue records through DNS when the zones are delegated, or configure your existing resolver's conditional forwarding to use **both** authoritative endpoints. Forklift does not change another resolver automatically. Validate representative forward/reverse queries through that resolver before changing clients. A pair of responding servers alone does not give clients failover unless their resolver configuration uses both.

## Outages, removal and recovery boundaries

A secondary continues answering previously synchronized zones after a primary/manager outage, including container recreation, until the SOA expiration interval is reached. It cannot receive new changes while the primary is offline. On recovery, native SOA checks resume transfers; reconciliation can request an immediate refresh. Primary failure does not promote the secondary or enable administrative writes there.

Removing a DNS node first revokes its transfer authorization at the primary, then removes its managed secondary zones. If either step fails, the record remains with an actionable removal error. Retry in the WebUI. After transfer revocation is confirmed, **Keep data; forget node** explicitly retains its remote copy and removes inventory. Stop/remove the old Docker stack separately through your hosting tool: a retained server can answer stale cached zones until expiration. No other DNS server or unrelated zone is deleted.

[TSIG](https://doc.powerdns.com/authoritative/tsig.html) authenticates transfers and detects tampering; it does **not encrypt** zone contents. Use trusted private networks or a VPN, and keep peer clocks synchronized because TSIG signatures have a bounded time window. HTTPS management uses a locally generated pinned RSA leaf certificate valid for one year; replace/reenroll a node before expiration. In-place remote certificate/transfer-key rotation is not implemented in this phase. Native API credential rotation for the local primary remains available.

Back up the secondary volume consistently together with matching Forklift metadata and installation secrets. **Existing encrypted Forklift backups still exclude DNS data/secrets volumes**; restoring LDAP metadata alone is not a coherent DNS restore. Integrated DNS recovery, supported bulk imports and broader upgrade/rotation workflows remain Phase 4. Do not reset existing LDAP or primary DNS volumes to add a secondary.
